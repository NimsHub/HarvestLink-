# HarvestLink common patterns

## Purpose

This document records the implementation conventions that should remain consistent as HarvestLink evolves. Examples describe the current plain-JavaScript prototype and the intended seam for a future persistent backend.

## Naming

- Entity collections use plural nouns: `products`, `requirements`, `reviews`.
- Entity identifiers use stable singular names: `productId`, `sellerId`, `buyerId`.
- DOM data attributes describe an action or target: `data-product`, `data-requirement-detail`, `data-modal`.
- Boolean helpers start with `is`, `has`, or `can`.
- Rendering functions use nouns for full views and descriptive nouns for components.
- Persisted database fields should use `snake_case`; browser model fields currently use `camelCase`.

Do not overload “bid” and “offer”:

- A product receives customer **bids**.
- A supply requirement receives seller **offers**.

## Application state

The prototype keeps:

- Persistent domain state in `db`.
- Current account identity in `db.currentUserId`.
- Ephemeral navigation/filter state in `state`.
- Rendered UI in `#app`.
- Temporary modal and toast UI in dedicated roots.

Do not place filter text, selected routes, or open-modal state into persisted domain records.

## Persistence adapter

Current persistence is deliberately isolated behind small helpers:

```js
function loadDb() {
  // Parse the HarvestLink localStorage value or clone the seed.
}

function saveDb() {
  localStorage.setItem(storageKey, JSON.stringify(db));
}
```

New features should not call `localStorage` directly. This makes it possible to replace the implementation with a repository/API adapter:

```js
const marketplaceRepository = {
  listProducts(filters) {},
  getProduct(productId) {},
  placeProductBid(productId, input) {},
  createRequirement(input) {},
  submitSupplierOffer(requirementId, input) {},
  acceptSupplierOffer(requirementId, offerId) {},
  createOrUpdateReview(input) {}
};
```

In production, methods become asynchronous and return server-authoritative entities. Views should render loading, success, empty, and error states.

## Seed and compatibility migrations

Prototype seed data provides predictable demonstrations. When a new optional field is introduced:

1. Load existing browser data.
2. Check whether the field is absent.
3. Derive a safe default.
4. Save the compatible structure.
5. Do not erase unrelated user activity.

```js
db.requirements.forEach(requirement => {
  requirement.status ||= requirement.acceptedOfferId
    ? 'accepted'
    : 'open';
});
```

Persistent database migrations must be versioned and reversible. Never translate the prototype's “patch on read” technique directly into production.

## Identity and role helpers

Use the shared accessors rather than repeatedly searching or comparing raw values:

```js
currentUser();
user(accountId);
isSeller();
isCustomer();
isDelivery();
```

Every protected interaction needs two checks:

1. A presentation check that hides or disables an invalid control.
2. An operation check immediately before changing data.

The production server performs a third, authoritative permission check. Client checks are never sufficient.

## Rendering and escaping

Views currently return HTML strings. All user-controlled strings must pass through `escapeHtml` before interpolation.

```js
`<h2>${escapeHtml(requirement.title)}</h2>`
```

Safe exceptions are:

- Numeric values that have been parsed and formatted.
- Known constant markup generated by application code.
- Trusted CSS class fragments selected from fixed application states.

Never interpolate user-provided HTML, URLs with unsafe schemes, event-handler source, or unvalidated CSS.

## Money and units

Use the shared `money(value)` formatter and always show the unit beside a product or offer price.

```js
`${money(product.currentPrice)} / ${escapeHtml(product.unit)}`
```

Production APIs should return a structured money object or integer plus currency:

```json
{
  "amount": 560,
  "currency": "LKR",
  "unit": "kg"
}
```

Do not perform monetary calculations with binary floating-point values.

## Navigation

Navigation is hash-based because GitHub Pages does not provide application fallback rewrites.

```text
#market
#product/p1
#requirements
#profile/u1
```

Navigation links use real `href` values so they support normal browser behavior. Programmatic navigation should update the hash and let the route function render the view.

When adding a route:

1. Choose a stable, shareable hash.
2. Parse only expected segments.
3. Handle missing entities with a safe fallback.
4. Update the routes table in [Project context](PROJECT_CONTEXT.md).
5. Test direct page load and browser back/forward.

## Event binding

Rendering replaces sections of the DOM, so event handlers must be rebound after a render. Centralize page bindings in `attachEvents` and modal bindings next to modal creation.

Use event delegation where repeated child controls share behavior. Avoid attaching multiple listeners to the same element through overlapping helpers.

Nested links inside clickable requirement cards must stop the card click without preventing the link's default navigation.

## Modal lifecycle

The modal pattern is:

1. Validate role and target entity.
2. Render into `#modal-root`.
3. Bind close/backdrop actions.
4. Bind the form or decision action.
5. Validate the operation again.
6. Update domain state and persist.
7. Close or rerender the modal.
8. Rerender the affected view.
9. Show a concise toast.

```js
saveDb();
closeModal();
render();
toast('Offer sent', 'The buyer can now review it.');
```

If the modal needs to show the result of an action, rerender it instead of closing it. Offer acceptance uses this pattern so the accepted row is immediately visible.

## Product bidding

Current prototype validation requires the next bid to exceed the visible current bid.

Production placement must be atomic:

```text
begin transaction
  lock product
  verify product is open
  verify customer is eligible
  verify amount > current bid
  insert bid
  mark previous highest bid as outbid
  update product.current_bid
commit
```

Return a conflict response if another bid wins the race. The UI should then refresh the live price and ask the customer to confirm a new amount.

## Supplier offers and acceptance

A seller has at most one active offer per requirement. A repeat submission updates that offer in the prototype.

Acceptance rules:

- The current account must be the requirement owner.
- The requirement must still be open.
- The offer must belong to the requirement.
- The selected offer becomes accepted.
- Other pending offers become declined.
- The requirement becomes supplier-selected.
- No new offers may be submitted afterward.

The persistent implementation must execute this transition in one transaction and emit an audit/notification event.

## Ratings

### Product ratings

- Authored by customers.
- Target exactly one product.
- Existing reviews become updates rather than duplicates.
- Relevant copy refers to product quality, freshness, packing, or consistency.

### Partner ratings

- Customer → seller or seller → customer.
- Self-rating is forbidden.
- Existing reviews become updates.
- Relevant copy refers to communication, reliability, fulfilment, or payment.

The prototype updates cached aggregates for immediate feedback. Production should calculate aggregates from published eligible reviews, either transactionally or through a reliable background projection.

When editing an existing review, remove its old rating from the aggregate before adding the new value. Never increment the count for an update.

## Status presentation

Domain status and visible wording are intentionally separated:

| Domain state | Visible wording |
| --- | --- |
| `open` requirement | Open requirement |
| `accepted` prototype requirement | Supplier selected |
| `pending` supplier offer | Accept offer available to owner |
| `accepted` supplier offer | Accepted |
| `declined` supplier offer | Not selected |

Use domain values in data and clear human wording in UI. Do not persist presentation-only phrases.

## Empty and error states

An empty state explains:

1. What is missing.
2. Whether that is normal.
3. The next valid action, when one exists.

Errors should be specific and recoverable. Examples:

- “Bid needs to be higher” plus the current amount.
- “Customer account required” plus the allowed operation.
- “No supplier offers yet” without implying failure.

Do not expose raw exceptions, tokens, storage contents, or server traces in user-facing messages.

## Dates and time

The prototype contains display strings such as “Just now” and “Closes in 5h.” Production entities store UTC timestamps:

- `created_at`
- `updated_at`
- `bid_closes_at`
- `needed_by`
- `verified_at`

Relative labels are derived at render time. Server time determines bidding eligibility and deadlines.

## IDs

The prototype may generate time-based string IDs for browser-only records. Production uses server-generated UUIDs or another collision-resistant identifier.

Never infer authorization, creation time, or entity type solely from an ID format.

## CSS conventions

- Use semantic component classes such as `.offer-card` and `.profile-hero`.
- Reuse custom properties for color and spacing.
- Avoid styling by element position or generated IDs.
- Keep mobile overrides next to the related component group.
- Add reusable visual behavior to [Style guide](STYLE_GUIDE.md).

## Testing pattern

For a cross-role feature, test the entire loop, not only form submission.

### Supplier-offer loop

1. Switch to a seller.
2. Open an unaccepted customer requirement.
3. Submit an offer.
4. Switch to the requirement owner.
5. Open supplier offers and accept one.
6. Verify the requirement displays “Supplier selected.”
7. Switch back to the winning seller and verify acceptance feedback.
8. Verify another seller sees the closed/non-selected state.
9. Refresh and confirm persistence.

### Rating loop

1. Open a product as a customer.
2. Publish or update a product review.
3. Verify review content and aggregate display.
4. Open a seller profile as a customer and submit a partner review.
5. Switch to a seller, open a customer profile, and submit a partner review.
6. Verify self-rating and invalid role combinations are unavailable.
7. Refresh and confirm persistence.

Always check the browser console after the end-to-end path.

## Deployment pattern

The repository deploys static files through `.github/workflows/pages.yml`.

For each publish:

1. Validate JavaScript with `node --check app.js`.
2. Review `git diff --check`.
3. Confirm documentation affected by the change is updated.
4. Push to `main`.
5. Confirm the newest GitHub Pages run succeeds.
6. Load the deployed URL with a cache-busting query when verifying new static assets.
7. Exercise the affected live workflow and inspect browser errors.
